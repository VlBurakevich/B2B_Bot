# Kaiten: Todoist-style interface + phone/Telegram access

Установка полного комплекта описана в корневом `../README.md`; он содержит точные Compose/Caddy-команды и порядок обслуживания тестового сайта.

Это подготовленный кандидат следующего обновления, а не заявление о работающем входе через общего бота. Исходный рабочий Kaiten и B2B не заменялись этой авторизацией. Визуальное обновление публикуется на тестовом домене отдельно; телефонный вход включается после согласования и установки доработки общего бота.

## Авторизация

- Только телефон + одноразовый код Telegram. Веб-маршрутов паролей, установки/сброса пароля и приглашений больше нет.
- Код: 6 цифр, 10 минут, полный интервал 60 секунд между запросами, до 5 неверных попыток; лимиты по номеру и IP. Только HMAC кода в БД.
- Одинаковый нейтральный ответ для неизвестного, pending, blocked и активного номера без права входа. Код отправляется только active + platform.full_access + подтверждённый собственный Telegram-контакт.
- Сессия 30 дней; случайный токен только в виде SHA-256 на сервере; cookie HttpOnly/Secure/SameSite=Strict. CSRF и точный Origin для изменяющих веб-запросов.
- Выход удаляет сессию. Блокировка, изменение прав и завершение сессий увеличивают auth_epoch и немедленно отзывают сессии/коды. Каждая API-операция проверяет актуальные статус и права. Проверка кода и создание сессии выполняются атомарно; отзыв во время отправки кода не позволяет войти.

API: `POST /api/auth/request-code {phone}`, `POST /api/auth/verify {phone,code}`, `GET /api/auth/me`, `POST /api/auth/logout`.

## Регистрация и доступы

В общем боте выбрать Kaiten → отправить собственный контакт → ФИО. Обязательны private chat, chat.id=from.id и contact.user_id=from.id. Телефон нормализуется в +7XXXXXXXXXX. Создаётся pending-карточка без прав. Администратору ставится уведомление в outbox; заявка видна в «Доступах».

Карточка хранит неизменяемый ID, ФИО, телефон, Telegram User/Chat ID, username, подтверждение контакта, даты регистрации/рассмотрения/изменения, status, role, access_version и расширяемый массив permissions. Статусы: pending / active / blocked. Карточки не удаляются. Действующие номера и TG-ID уникальны; блокировка не освобождает их.

В «Доступах»: одобрение/блокировка, роль сотрудник/руководитель, отдельные права, завершение сессий, журнал входов и действий администратора. Последнему администратору нельзя закрыть доступ. Изменения защищены версией карточки. Каталог прав находится в access.py, финансовых модулей и прав B2B нет.

## Существующие аккаунты

Миграция сохраняет ID пользователей, авторов, исполнителей, участников, проекты, задачи, вложенность, сроки, файлы, комментарии и историю. Старые сессии завершаются, приглашения закрываются. Старое поле telegram_chat не считается доказательством собственного контакта.

Сотрудникам однократно сохраняются их прежние рабочие возможности в виде прав; руководителям — управление доступами, назначение и обзор компании. Телефонный вход всё равно требует подтверждённого контакта.

Первый руководитель сохраняет свой существующий аккаунт. После подтверждения контакта в боте оператор сервера выполняет сначала просмотр, затем явную привязку по точному ID, телефону и TG-ID:

```sh
python identity.py --account-id EXISTING_ID --telegram-id VERIFIED_TG_ID --phone +7XXXXXXXXXX
python identity.py --account-id EXISTING_ID --telegram-id VERIFIED_TG_ID --phone +7XXXXXXXXXX --apply
```

Совпадение имени нигде не используется. Если уже создана pending-карточка, она сохраняется как заблокированная историческая карточка со ссылкой linked_to на прежний аккаунт; её подтверждённая личность переносится на прежний ID. Карточка и исходные телефон/TG-ID остаются для аудита. Привязка запрещена, если у новой pending-карточки неожиданно есть рабочие данные.

## Общий бот

Действующий бот размещён у программиста и не изменялся. Готовая доработка и инструкция — в `../bot/`. Она сохраняет текущие токен, webhook-настройки, B2B_ORIGIN и BRIDGE_KEY. Для Kaiten нужен новый независимый канал и ключ. Не запускать getUpdates из Kaiten: `telegram_worker.py` только доставляет уведомления через подписанный канал общего бота.

Подпись Kaiten имеет собственный домен, service ID, timestamp, nonce, path и SHA-256 тела. Повторы и другой сервис отвергаются. У тестового и основного Kaiten разные service ID, ключи и базы. Клиент требует health протокола 3 с точным service/origin и не отправляет код в старый B2B-канал.

## Безопасное включение

1. Отдельно согласовать доработку общего бота и установить её на его сервере по ../bot/README.md. Проверить B2B и подписанный health Kaiten.
2. Остановить прежний тестовый сервис на согласованное окно обслуживания, затем подготовить кандидата с отдельной копией **тестовой** базы/файлов и выполнить миграцию вне прежнего процесса. Не допускать параллельных записей; производственные данные не использовать для демонстрации.
3. Временно направить на кандидата только подписанный `/api/telegram-bridge/message` тестового домена; остальные запросы показывают страницу обслуживания. Это позволяет владельцу подтвердить контакт, пока прежняя база защищена от параллельных изменений.
4. Привязать подтверждённый контакт к существующему тестовому аккаунту руководителя по точному ID. Проверить хотя бы одного eligible администратора, platform.full_access и admin.access.manage.
5. Сохранить исходную тестовую базу, код и Caddyfile; остановить только тестовый сервис и переключить его на подготовленного кандидата. Убедиться, что веб-интерфейс и endpoint бота используют одну базу. Не смешивать данные кандидата с параллельными правками старого тестового стенда.
6. Проверить реальные сценарии входа и доступа. Основной Kaiten обновлять только отдельным согласованным этапом: с остановкой его процесса, свежей резервной копией и миграцией актуальной базы, сохраняя все ID. Не подменять рабочую базу устаревшей копией или демобазой.

До готовности бота и первого подтверждённого руководителя полный переход не выполнять: иначе прежние сессии будут закрыты, а получить код будет некому.

## Проверка и локальный стенд

Python 3.12+, зависимости в requirements.txt:

```sh
python -m unittest discover -s tests -v
node --check static/app.js
node --test ../bot/test/*.test.mjs
```

61 Python-тест и 15 тестов общего бота прошли. Покрыты миграция, бизнес-сценарии, код/сессии/лимиты, конкурентные проверки и отзывы, права, подмена контакта, подпись, повторы и независимость сервисов. Доставка Telegram в тестах заменена заглушкой.

`seed_demo.py` создаёт вымышленные идентичности только при KAITEN_DEMO_MODE=local-fixture, loopback PUBLIC_URL и отсутствии реального bot bridge. На публичных серверах этот режим не использовать. Подмена доставки AUTH_SEND разрешается только при TESTING=True, в релизном окружении она не включена.

Файл phone-auth.key генерируется атомарно с правами 0600 в DATA_DIR. Сохранять его вместе с защищённой резервной копией данных; не публиковать. Секреты, базы, загруженные файлы и ключи не входят в архив исходников.
